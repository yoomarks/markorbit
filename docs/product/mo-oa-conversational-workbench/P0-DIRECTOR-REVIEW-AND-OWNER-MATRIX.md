## 2. 产品总监决定

P1 优先交付 Lite 专业 OA 解读的真实可操作、高保真 fixture Preview；P2 在受控专业审核输出与客户授权投影具备后接 Customer Portal。
用户的第一问题是“这份文件要求什么、何时要确认、我需要做什么”，但任何答复期限必须来自经过准入且具备明确依据的精确文件/官方源；不能从国家默认期限、模型估计、内部生命周期推导。
用户从现有商标资产、Formal Matter 或已授权 OA 文件进入，不增加一个与资产/案件无关的空白万能聊天页。
支持多份 OA、多页、多问题、文件替换、同案件多法域和客户补件；模糊匹配必须审查确认。
工作成功 = 有来源的问题清单、事实缺口、资料请求和待审核分析/答复准备成果；“模型回复成功”不算完成。
直客与专业用户共享精确业务/证据引用，但专业内部备注、未审法律分析及其他客户私有数据不能向直客公开。

## 3. 设计总监决定

布局遵循列表/详情分离：大量商标或文件用独立检索列表；进入一个案件/文件后用上下文任务台。仅少量固定设置才用左右 Master–Detail；不在详情底部重复完整文件列表。
桌面优先显示当前案件与文件、问题导航、所选问题原文证据、MO 逐步澄清、待审核成果；允许紧凑双栏或三栏，不强制所有页面三栏。
390px 采用单任务顺序，原文/证据和成果为明确可返回的完整视图；无需在小屏幕压缩三个面板。
对话控件：文件选择与版本卡、可能案件匹配确认卡、问题卡、原文片段与定位、可信来源及识别置信度、补充资料卡、专业意见编辑卡、来源冲突卡、审核与保存卡。
每张问题卡分开展示“原文要求”“MO 待核对解读”“用户提供的信息”“专业审核结果”，不能用一个绿色状态混同。
简体中文默认、完整自然英文。官方原文、商标、申请号、商品服务、用户输入和文件名在语言切换时保持不变；译文须显式标明为说明。

## 4. 技术总监决定：真相与安全

OA 原件及规范化版本应由现有授权的文件/Knowledge Owner 持有；当前私有绑定合同只是可复用语义，不据此新建第二原件库。
正式 Workspace/Case/Asset 关联由相应 Owner 准入；建议匹配是候选，不得自动写入正式客户、资产或 Matter。
OA 解读由 Brain/Capability 在授权原文及治理方法下准备，标记模型/方法版本和每项结论的来源定位；缺失生产调用时 Preview 使用显式 fixture，不伪造模型、OCR 或法律结论。
正式专业审核、准备、递交和发送由既有专业/Execution Owner 负责；本 P1 只能生成本地 Demo 草稿/回执，不能发布客户可见正式建议。
MarkReg Examination 是内部流程信息，只作为相关上下文显示，不可作为“已收到 OA / 无 OA / 期限存在/不存在”的依据。
可信 Subject + Workspace + exact Case/Asset/File grant 是读取与恢复条件；URL 中的申请号、文件名、聊天文本、Site 来源不能授予权限。
审查员通知正文是未受信输入；文档内指示不得改变模型系统规则、执行工具或跨租户查询。
不得上传私有 Workspace 原件到公共 Data Engine，不得从私人文件自动推广成 DATA_ENGINE_FACT。

## 6. P1 Lite 专业试点（一个独立 PR）

一份显式虚构的 OA fixture，包含两个独立问题、带页/段定位的原文片段、可信文档标识、案件版本，以及“期限未证实”场景。
流程：由授权案件/文件入口进入 → 核对文件/案件匹配 → 查看有来源问题卡 → 选择问题并核对原文 → MO 提出一个有界问题 → 专业人员补充证据及客户待补信息 → 生成可编辑待审核摘要 → 审核后保存 Demo 草稿 → 返回原案件。
修改原文件版本或案件版本必须让依赖它的待审分析失效；刷新及切换语言不得改变证据、用户原文或草稿身份。
生产 OCR、法律意见、自动生成正式答复、公开给客户与发送/提交均不在 P1。

## 7. P2 Customer Portal（等 #1441 安全集成后）

从本机构该客户的具体 Matter/消息进入，仅展示明确获准公开的 OA 说明及客户待补资料卡。
没有专业批准的分析，不显示假定的结论；机构内部审阅意见、证据冲突与私有工作日志不能由客户端过滤代替服务端权限。
客户上传资料若上传 owner 未就绪，只能标记演示；真实资料保存必须有 owner receipt、权限及版本绑定。
客户看到“已提交资料”不等于 OA 正式答复已递交，也不等于费用已支付。

## 8. 必须验收的反向矩阵

跨 Workspace/跨客户/代表权过期、被撤销文件授权、源文件缺页、无法读取 OCR、候选案件不唯一、文件替换、历史/冲突证据、来源服务 503、期限未知、模型失败、草稿被修改、刷新重进、重复点击确认及文档内指令注入。
区分 LOADING、NO_SOURCE、AMBIGUOUS、PARTIAL、PERMISSION、STALE、UNAVAILABLE、PREPARED、REVIEWED_DEMO 与保存失败；未知或失败不能变成“无 OA”或“无期限”。
验收同时覆盖中文/英文、桌面/390px、键盘、文本放大、屏幕阅读器标签；无来源的摘要不得呈现为已核准官方事实。

## 9. 三总监门禁与任务拆分

产品门禁：完成实际用户工作，从文件原文到可审材料；每个问题有下一步，不把聊天条数当成功。
设计门禁：来源、当前步骤、客户/专业可见性清晰；大列表与详情不重复；实际两端高保真复核。
技术门禁：没有第二套 owner、无跨租户泄漏、来源版本 fail-closed、无虚假官方期限/模型/递交回执。
P1 为 Lite fixture-only UI；P2 是 Customer Portal 的独立消费者；P3 由文件/Knowledge、Brain/Capability、Workspace/MarkReg owner 各自按缺口分 PR 建立生产路径。
本 P0 只交付决议、对象/Owner 矩阵与 P1 Codex 合同；不修改生产合同或提交保护动作。
