## 3. Identity and current Provider API authority

```text
Provider Workspace identity = existing Core Workspace identity
referenced by existing MGSN providerWorkspaceId
```

Core owns users, sessions, membership, permissions and Workspace identity. MGSN `providerId` is an operational/provider-network reference, not another organization. Reuse the single Registry binding; no ProviderAccount, ProviderOrganization, MgsnWorkspace, NetworkWorkspace or ProviderLogin identity. Missing valid binding is not permission to auto-create a Provider or enroll in the network.

**Implemented:** Provider requests choose context using `x-markorbit-provider-workspace-id`; this header alone is not authority. Gateway combines it with the session cookie and calls Core `resolveWorkspace`. It requires `execution:read` for GET and `execution:manage` for POST; mutations also require trusted Origin and valid session-bound CSRF. Missing context is 400, missing session with context is 401; unavailable authentication/MGSN dependencies fail closed with 503-class errors. MGSN requires trusted internal authentication plus a parsed Workspace Principal and repeats the permission check.

Gateway rejects Provider mutation payloads containing `providerId` or `providerWorkspaceId` with `PROVIDER_IDENTITY_PAYLOAD_FORBIDDEN`, even if the values appear correct. MGSN supplies `principal.actorId = principal.userId` and `principal.providerWorkspaceId = principal.workspaceId` after spreading the body. The domain resolves the Provider from that trusted Workspace and checks the allocated Provider. Body actor/principal fields cannot override trusted attribution. Existing payload `workspaceId` is the **originating/customer Workspace**, checked against work lineage; it is not the Provider Workspace. Do not replace it with the Provider's ID or treat it as a second identity claim.

| Current Gateway API                                    | MGSN equivalent                                       | Current behavior to REUSE                                                                                                                                                                                         |
| ------------------------------------------------------ | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/provider/allocations/:allocationId`          | `GET /v1/provider/allocations/:allocationId`          | GET permission; optional exact `version`; record must have `allocation.provider.providerWorkspaceId === principal.workspaceId`. Missing and wrong-Provider records both return 404 NOT_FOUND.                     |
| `POST /api/provider/allocations/:allocationId/respond` | `POST /v1/provider/allocations/:allocationId/respond` | Trusted Provider response with originating `workspaceId`, expected Allocation version, decision, acknowledgement, correlation and Idempotency-Key; section 5 exact M4 checks. Returns Provider Acceptance record. |
| `POST /api/provider/returns`                           | `POST /v1/provider/returns`                           | Trusted Provider creates/corrects Return against exact Allocation/ACCEPTED response/Service Package lineage, expected versions, claims/evidence and idempotency.                                                  |
| `GET /api/provider/returns/:providerReturnId`          | `GET /v1/provider/returns/:providerReturnId`          | GET permission; optional exact `version`; `record.providerWorkspaceId === principal.workspaceId`, otherwise 404 NOT_FOUND.                                                                                        |

MGSN mutations require a nonempty `Idempotency-Key`; if the body also supplies it, the values must match. Domain fingerprints bind actor/Provider Workspace, originating work scope, payload and versions. These routes are ID-based: there is no Provider allocation list, Return list, aggregated work queue, profile self-service endpoint or Provider-side Acceptance GET in this family. Allocation GET does not embed its response; do not infer Acceptance from Allocation `ACTIVE`.

Wrong-Provider GET non-disclosure is implemented. Existing domain mutation errors distinguish missing records, identity/Workspace mismatch (including 403) and stale/conflicting versions (409); do not describe all mutation errors as identical 404s. Future product extensions must preserve fail-closed ownership and privacy-safe responses, and must not use errors or ID probing to discover another Provider's work.

## 5. Exact existing M4 behavior

**Implemented; not new product states:**

| Record / operation            | Exact behavior                                                                                                                                                                                                                                                           |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Service Package / Eligibility | Package statuses ADMITTED / STALE / CANCELLED; Eligibility outcomes ELIGIBLE / INELIGIBLE. Existing admission and Allocation checks remain owner-controlled.                                                                                                             |
| Allocation                    | Contract statuses ACTIVE / CANCELLED / SUPERSEDED. Explicit creation uses current exact admitted Package, ELIGIBLE evaluation, Provider/Supply versions and source fingerprints. No Provider claim/allocate action or cancellation API is introduced here.               |
| Acceptance                    | Decisions ACCEPTED / DECLINED, one response per Allocation. Before a new response: exact ACTIVE Allocation version, originating Workspace/correlation, no existing response, trusted Workspace's Provider matches allocated Provider, and Provider operationally ACTIVE. |
| ACCEPTED                      | Records the response; Allocation stays ACTIVE. No appointment, blanket data grant, filing or completion.                                                                                                                                                                 |
| DECLINED                      | Records the response and appends a next Allocation version with SUPERSEDED status, preserving the original version; later reallocation is separately governed. Not an editable response or automatic alternate choice.                                                   |
| Return                        | Requires current ACTIVE Allocation, exact ACCEPTED response matching Provider/Allocation, exact ADMITTED Package and correlation, ACTIVE Provider, and at least one artifact or structured assertion. Records CURRENT with `submittedAt` and fingerprint.                |
| Return correction             | Explicit `supersedes` must identify the exact current Return and same lineage. Reuses Return ID, increments version, preserves SUPERSEDED history; creating another current Return without explicit correction conflicts. No second draft/submission lifecycle.          |

Existing response/Return replay resolves an exact committed fingerprint **before** new operational/current-lineage checks. Thus an authorized exact retry can return historical success after Provider restriction or source change; it is not a fresh mutation or proof of current usability. Different payloads under the same key conflict. Future work/read projections must distinguish recorded result from present action/data authority, especially when retries occur after Handoff expiry/revocation.

**Operational restrictions:** Registry statuses remain ACTIVE / SUSPENDED / INACTIVE. Creation requires active Core identity; reactivation checks Core again; INACTIVE is terminal in the implemented Registry. New response (including DECLINED) and new Return/correction require ACTIVE Provider. Do not promise “decline while suspended” as an existing exception. New Supply creation rejects INACTIVE; Supply revision currently checks exact Supply version and referenced Provider existence without the same ACTIVE-only restriction. Neither operational management path thereby becomes Provider self-service.

Provider Allocation/Return GET checks permissions and recorded Provider Workspace ownership, not current Provider operational status, Participation or Handoff. Historical exact-version reads therefore do not require Provider ACTIVE in those handlers. A future product must label restrictions without inventing a new account status, deleting history or claiming all old fields already have V1 disclosure enforcement. Any changed mutation policy requires separately reviewed M4 work, not a UI override.

## 7. Before and after Acceptance: the same privacy boundary

Before response the Provider may see only its authorized Allocation metadata and any separately authorized incoming projection necessary for the exact review purpose. After ACCEPTED, the Provider still sees only exact authorized data. Acceptance is not the privacy gate; DECLINED, SUPERSEDED and old ACCEPTED history likewise cannot grant incoming access.

**Current limitation:** Provider GET returns the existing Allocation/Return record, including operational references and free-text fields such as Allocation `rationale` or Return assertions; it does not implement a Handoff field filter, source-rights check or complete product-safe projection. REUSE means preserve the authenticated operation and exact M4 semantics, not render every raw field. The future A/B projection must explicitly allowlist metadata and review free text, reference labels and filenames for privacy. Do not silently expand current M4 data or claim that V1 privacy validation already runs.

```text
Provider Workspace read != blanket access to Originating Workspace records
Handoff authorization != delivery != Provider Workspace access
```

An incoming-data endpoint is an **actual disclosure**, even if implemented as GET, cached view, preview or download. Before each disclosure it must validate the authenticated exact recipient Provider Workspace/binding; exact current #405 Handoff and required current #394 Selection; purpose, field allowlist and immutable source/version; finite validity, expiry/revocation and current owner field rights; relevant Participation/Visibility/Trusted relationship, Provider operational/Supply state and required #375 proof. Enforce the separate delivery/access action authority; a bearer envelope ID, ACCEPTED result or cached historical fingerprint is insufficient. Recheck at use after races; fail closed on unavailable authority. No cross-service SQL or consumer-database reconstruction of missing customer context.

When an envelope expires/revokes or source/permission becomes stale, stop new disclosure and cached re-serving under it, including artifact retrieval. Do not erase lawful historical Allocation/Acceptance/Return facts or rewrite past delivery. Restricted historical reads use their own current authority and cannot republish withdrawn data. A separate existing professional obligation must be established by its canonical owner; this document creates no exception or cancellation semantics. Future product cache invalidation and rendering must clear unavailable projections without claiming that already delivered knowledge can be erased.

## 8. Return and action authority

Provider Return = Provider claim + structured evidence/reference. Reuse CURRENT / SUPERSEDED, exact accepted lineage, `workStatusClaim`, artifacts/assertions and correction rules from section 5. A claim such as WORK_COMPLETED or a filing reference remains a claim; it is not a new lifecycle state, filing confirmation, Matter completion, payment truth, Official Truth or Capability verification.

AI may summarize authorized instructions, explain an Allocation, assist a human decision, draft Return content, check completeness and flag missing evidence. It may not execute Acceptance or submit/certify Return for the Provider, appoint, send protected external action, file, pay or mark a Matter complete. Any separate canonical protected authority would need its own approved boundary; none is created here. Human Return submission through M4 is not an automatic external evidence handoff or professional certification.

M4 Evidence Handoff remains the separately authorized originating-Workspace operation for exact Return/Execution lineage. M13 Provider instruction remains independently protected and preserves `targetOwner = MGSN`, `providerEngagementCreatedByExecution = false`, `providerAcceptanceCreatedByExecution = false`. ## 9. Participation, responsibility and admin separation

Provider operational status, Core Workspace access, Participation, Visibility, direct-executor proof, Acceptance and Handoff validity are separate axes. No-row Participation is NOT_PARTICIPATING/PRIVATE. PAUSED/REVOKED participation stops applicable new discovery/network exposure and denies new Handoff reliance under #395; it does not disable Core identity by itself or delete Provider-owned lawful Allocation/Acceptance/Return/audit history. Historical access still needs normal authenticated authorization; it does not retain withdrawn incoming disclosure rights. Current M4 handlers do not check the future Participation axis, and #406 does not add that check to existing M4 mutations.

Provider Workspace is the natural future maintenance surface for #375 final-executor status, direct responsibility, no-rebrokering commitment/violation state, necessary legal signer/entity disclosure and evidence/attestation references. Consume its authoritative version, source, effective period, freshness and suspension/revocation semantics. Provider-submitted attestations are not automatic verified proof. ACTIVE Provider or past successful work never proves final execution; unknown/unproven must display honestly and fail closed where proof is required. Do not encode responsibility into `operationalStatus` or backfill Providers as proven executors.

Transparent legally required signer != hidden rebrokering; signer disclosure != recipient access right. A signer receives no implicit data, team access or onward-transfer authority. Hidden broker/sub-agent chains cannot appear compliant. No forwarding/reselling work to an undisclosed Provider.

**Operations Console != Provider Workspace.** INTERNAL_OPERATOR plus `commercial-admin:read` remains internal operator authority; a Provider user cannot inherit it. A human who independently has both roles must use separately authorized contexts, not role blending or admin results laundered into Provider views. Do not expose Operations Console to Providers as the product shell.

No marketplace dashboard, lead market, bid room, cheapest-provider auction, broker console, sub-agent network, customer-job browse, arbitrary claim/bid/resell/forward or automatic Selection/Allocation/Acceptance. Work reaches the Provider through governed MGSN authority.
